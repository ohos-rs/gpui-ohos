## 发现

### 1. P1：帧回调配置失败会吞掉 SurfaceCreate

位置：Ability `crates/ability/src/render/xcomponent.rs:378`。

`configure_frame_callback(...)?` 位于 `Event::SurfaceCreate` / 子窗口创建通知
之前。原生注册或注销返回错误时，回调直接返回；底层 XComponent 回调入口
丢弃这个 Result，系统 Surface 已激活，但 GPUI 收不到创建通知。
GPUI 的 `on_finish_launching` 仅在首次 SurfaceCreate 时调用，因而初始化可能
停在空白页；Surface 重建时也可能无法恢复。移动配置调用之前，创建通知会先发送。

必须把 Surface 生命周期通知与帧源配置结果分开：总是报告有效的 Surface 创建，
由帧源管理器记录配置失败并选择可用帧源。需要覆盖注册失败、注销失败、
运行中 RequestFrame 失败三个场景；先前只强制验证了 VSync 创建失败。

证据级别：生产调用链静态确认；本次未在模拟器注入这些原生失败。

### 2. P2：CPU 繁忙会触发后台线程过度扩容

位置：`src/ohos/task_queue.rs:108`、`src/ohos/dispatcher.rs:90`。

监控器以 10 ms 内没有新的出队记录判断阻塞。这个条件同样适用于所有 worker
正在执行较长的计算任务，无法证明需要增加线程。队列持续有积压时继续创建线程，
可能增加调度竞争、栈内存和前台输入延迟；创建线程失败还会让监控线程 panic 退出。

主机复现直接编译当前生产 dispatcher/task_queue，使用真实 GPUI executor 和
GPUI 优先级主队列，只有原生 UI wake 使用计数桩。64 个任务各自持续计算约
300 ms，计时区间内无 IO、睡眠或锁等待：基础 worker 为 8，观测到 **30 个
worker、最多 30 个同时尚未返回的 poll**。这是扩容机制的复现，不是真机功耗
或固定工作量的吞吐性能结论。

更好的方向是 OHOS 系统调度和 QoS，优先验证 FFRT 接入，而不是继续调整 10 ms
阈值。不能用固定小线程池替代后宣称能力对齐：阻塞父任务等待子任务必须继续推进。

### 3. P2：Pan 起点未重置累计偏移，丢失终止事件后会反向跳动

位置：Ability `crates/ability/src/render/xcomponent.rs:57`、`:157`。

`PanDeltaTracker::next(Start, ...)` 仍减去上一段保存的 offset；只在 End/Cancel
时清理。原生输入快照缺失会在调用 tracker 前返回，也没有在新的 Start 上隔离
上一段手势。生命周期切换或系统终止通知缺失的情况下，状态可以跨手势保留。

从生产源码逐字提取 tracker 后复现：上一段 offset 为 -240；未收到可处理的
End/Cancel；下一段系统 Start offset 为 -12；输出为 **+228**，应为 **-12**。
这确认了缺失终止通知后的错误计算，尚未确认当前 phone 系统会产生哪一种缺失
序列，不能据此断言它就是此前真机闪跳的唯一原因。

必须在每次系统 Start 上重置累计基线；Cancel 的收尾不能依赖可选坐标快照；
Surface 代次变化必须取消手势状态。继续使用系统位移和速度，不增加自定义识别门槛。

### 4. P2：去重依据是当前 bounds，可能漏掉 Surface 重建后的尺寸通知

位置：`src/ohos/window.rs:1136`、`:1195`、`:1257`。

已有 GPUI 窗口的 Surface 以新尺寸重建时，`initialize_renderer` 先改写平台 bounds，
但普通无键盘场景不会发送 resize。随后相同新尺寸的 WindowResize 被新增的
`size_changed` 判断跳过。若没有移动、焦点变化等额外通知触发同步，GPUI 仍保存
旧的 `viewport_size`，造成布局与新 surface 不一致。

GPUI `window.rs:2691` 明确只在 `bounds_changed` 中从平台刷新该视口；单纯请求帧
不能替代尺寸通知。必须按“上次已通知 GPUI 的有效尺寸和 scale”去重，并在 Surface
重建后同步一次。验证场景应为 Surface 重建期间尺寸改变、窗口位置/焦点不变。

证据级别：生产调用链静态确认；本次未在模拟器复现该特定事件顺序。

## 系统能力与其他平台对齐方案

| 边界 | 当前情况与建议 |
| --- | --- |
| 后台任务 | 自建弹性线程池是主要替换候选。macOS 和 gpui-mobile iOS 使用 GCD，Windows 使用系统线程池。OHOS 优先做 FFRT 原型，映射 GPUI 优先级至系统 QoS。 |
| FFRT 兼容性 | 必须验证 Rust TLS、同步锁、嵌套等待、取消与销毁语义。FFRT 默认协程模式可能在恢复时更换线程；API 20 提供 queue thread mode。接入必须覆盖已有最低 API，不能静默提高系统版本要求。 |
| UI 唤醒 | 保留 N-API 主线程派发和唤醒合并；明确入队是否成功及 session 生命周期。UI future 及其销毁继续留在所属线程。 |
| 帧驱动 | 系统 NativeVSync 按需请求方向合理。保留旧回调的代次防护；将 VSync 与 XComponent fallback 的切换集中在一个所有者，避免不同层重复缓存注册状态。 |
| 手势 | 保留 XComponent 原始接触和 ArkUI Pan 位移/速度。可进一步以 ArkUI Tap/LongPress 取代适配层点击/长按计时，但必须完整保留控件捕获、双击、抓停不误点击、IME、Cancel 和多指语义后再切换。 |
| 惯性 | Pan End 只给释放速度，GPUI 自绘内容仍需后续推进。当前 SDK 通用 Animator 的 friction easing 不能直接视为 Scroll 的完整惯性模型；先确认可独立驱动自绘内容的系统接口，否则保留单一惯性状态与系统 VSync，避免再加第二套时钟。 |
| 尺寸 | 用系统 surface/content rect、avoid-area 等作为输入，集中发布有效 viewport；去重基于已发布值。 |

本次在线核对 gpui-mobile 的 HEAD 为 `9075e3a`：
[iOS dispatcher](https://github.com/longbridge/gpui-mobile/blob/9075e3aa3eea812127f2c60ed66f0cd5798ff245/src/ios/dispatcher.rs)
使用 GCD；[iOS touch](https://github.com/longbridge/gpui-mobile/blob/9075e3aa3eea812127f2c60ed66f0cd5798ff245/src/ios/window.rs#L908)
和 [Android touch](https://github.com/longbridge/gpui-mobile/blob/9075e3aa3eea812127f2c60ed66f0cd5798ff245/src/android/window.rs#L1453)
将原始触摸送入 GPUI，并使用 FlingGuard。不能把它描述成由 UIKit/OverScroller
完整接管滚动。其 FlingGuard 文档还明确说明抓停后不误点击的语义未完整恢复，
因此不能直接替换当前 OHOS 方案。

FFRT 依据为[官方开发指南](https://github.com/openharmony/docs/blob/master/en/application-dev/ffrt/ffrt-development-guideline.md)
及[官方 C API](https://gitcode.com/openharmony/docs/blob/master/en/application-dev/ffrt/ffrt-api-guideline-c.md)，
并核对本地 API 26 NDK 的 `ffrt/task.h`、`ffrt/queue.h`。FFRT 是优先验证方案，
本次没有把未经设备验证的原型计作可交付实现。

## 已有优化的评价与验证边界

- 按需 NativeVSync、帧代次、唤醒合并、设备级 shader/layout/pipeline 复用、逐行
  像素转换，以及先释放 native 消费者再释放 RootNode，方向合理，建议保留。
- 原子状态位本身不是目前发现的性能热点。跨层重复状态及缺失的失败/重建收尾
  比位数更值得处理。`FrameRequest` 的 REQUESTED 和 PENDING 可同时存在，不能
  简单合成一个布尔值；代次用于隔离旧回调，也应保留。
- 最新移除 `target_env` 等非 OHOS 分支的提交未发现额外 OHOS 行为回归；
  `desktop/mobile` 是 OHOS 设备类别，保留合理。
- 本次重跑生产模块主机回归 **33/33 通过**。这些测试不能覆盖以上原生错误注入、
  Surface 重建和缺失终止通知；通过不能据此证明所有边界正确。
- 本次没有新增模拟器/真机验证，也未重新打包。之前的模拟器通过记录仍只覆盖
  当时列明的场景；真机发热不能由本次主机扩容探针直接解释。
